## 4. Platform-specific branches

**No `#if UNITY_ANDROID` / `UNITY_IOS` / `UNITY_VISIONOS` branches exist anywhere in
`Assets/Scripts`.** No `Application.platform` or `RuntimePlatform` checks. Part 8 CR-1
appears to pass on a naive grep.

It does not actually pass. **The platform fork is `Assets/xrviz.asmdef`:**

```json
"includePlatforms": [
    "Android", "Editor", "EmbeddedLinux", "LinuxStandalone64",
    "macOSStandalone", "WindowsStandalone32", "WindowsStandalone64"
]
```

This is an allowlist with **no Apple XR target**. Every script in `Assets/Scripts` is
excluded from a visionOS build today. The visionOS port cannot compile a single line of
ERUPT code until this changes.

The only preprocessor directives in the codebase are `#if OPENCV_FOR_UNITY` in
`MarkerRobotPlacement.cs:13, 19, 80`. This is an optional-package presence guard, not a
platform check — see §7.

`Temp_VisionOS/` exists at the repo root and is a **plain `Unity-VisionOS.xcodeproj`**
(fully-immersive / Metal). `Packages/manifest.json` contains **no PolySpatial package**.
Guidelines Part 6 assumes PolySpatial mixed reality. These are inconsistent — see §7.

## 5. Current interaction flows

### 5a. Create an obstacle
Left-controller `Menu` action → `WristMenuController.OnMenuToggle:362` → wrist panel →
`Add Shape` → `Add Cube` → `AddPrimitiveShape:635`:
`GameObject.CreatePrimitive` → placed 2 m along `Camera.main.forward` → kinematic
`Rigidbody` → `XRGrabInteractable` (`SelectMode.Single`) → `SelectableGrabController` →
four grab transformers → `CollisionObjectPublisher` with id
`unity_{type}_{DateTime.Now.Ticks}` → `SelectionManager.SetSelectedObject` →
inserted into `objectsById`. Publisher's next `Update` emits ADD on `/collision_object`.

### 5b. Edit an obstacle
Two disjoint paths.
- **Direct manipulation:** ray-select → `SelectableGrabController` enables the
  `XRGrabInteractable` → grab/move/two-hand-scale via XRI transformers → publisher detects
  transform change → MOVE on `/collision_object`.
- **Menu:** wrist → `Edit Shape` → `PopulateEditShapePanel:448` sniffs
  `MeshFilter.mesh.name` for `"Cube"`/`"Sphere"`/`"Cylinder"`/`"Mesh"` → builds
  toggle+slider stacks → slider delta feeds `XRUIScaleTransformer.queuedDelta` if grabbed,
  else writes `transform.localScale` directly (`:225-238`).
- `Snap Surface` → `SnapSelectedToSurface:784` → `Physics.RaycastAll` downward for a
  `"SnapSurface"`-tagged collider.

### 5c. Set a goal
`MoveItPlanningRequestMenuUI.OnSetGoalStateClicked:477` → `ghostSpawner.SpawnGoalGhost()`
→ `GetGoalRobotState()`. The arm is posed beforehand via the IK handle:
`Quest3ControllerRayInteractor` grip-press → `Quest3RobotInteractionController.TryBeginHandleDrag`
→ `DirectArticulationIKController.SolveToTarget:107`. Joint jog: thumbstick Y →
`JogSelectedJoint` → `NudgeJoint:149`.

### 5d. Request a plan
`SendPlanningRequest:502` → validates start+goal → `CreateMotionPlanRequest()` →
`GetMotionPlanRequest` on `/plan_kinematic_path` → `OnMotionPlanResponse:645`.
MTC path instead: `PickPlaceTaskRecorder` publishes `/pick_place_task`; the ROS demo node
plans and republishes `/description`, `/statistics`, `/solution` at 1 Hz.

### 5e. Preview a trajectory
- MoveIt: `TrajectoryReplay` + `SpawnGhosts`.
- MTC: `MTCDashboardPanel.OnPreviewClicked:483` → `MTCTrajectoryPlayer.PlaySolution` →
  saves pose, walks `sub_trajectory`, applies `scene_diff` attach/detach (`:77`), restores
  pose on stop.

### 5f. Execute on hardware
- MoveIt: `executeTrajectoryButton` → publish on
  `/joint_trajectory_controller/joint_trajectory`.
- MTC: `OnExecuteClicked:495` → `MTCDataManager.PublishExecuteSolution` → `UInt32Msg` on
  `/mtc_execute_solution`; status back on `/mtc_execution_status` (String). Actions are
  bridged this way because the ROS-TCP-Connector submodule has no action support.

## 7. Guideline conflicts and ambiguities

Stated plainly rather than worked around silently, per the prompt.

**C1 — XRI 3.2.1 already is an interaction abstraction.** Part 3's Backend→Router→
Interactable split overlaps XRI's Interactor/Interactable model. Reimplementing it would
mean rewriting working grab, two-handed scale, and attach-controller push/pull physics.
*Chosen interpretation:* XRI's device-facing half becomes the OpenXR **backend**; XRI
grab transformers are treated as **Interactables** and adapted; the Router is new code.
Part 8 CR-2 is enforced against raw `InputDevice`/`InputAction` reads, with XRI interactor
callbacks permitted only inside backend-assembly adapter classes.

**C2 — Part 8 CR-1 says "no platform preprocessor directives," but the real fork here is
an asmdef allowlist.** A literal grep for `#if` passes today while the codebase is
completely unbuildable for visionOS. *Chosen interpretation:* enforce the boundary with
per-platform assembly definitions, which is structurally stronger — feature code cannot
reference platform code that its assembly does not reference.

**C3 — `#if OPENCV_FOR_UNITY` is not a platform branch.** It guards an optional package
that the README says is not included. Kept; logged to backlog rather than counted as a
CR-1 violation.

**C4 — Part 6 assumes PolySpatial; this repo does not have it.** `Temp_VisionOS/` is a
fully-immersive Metal Xcode project and `manifest.json` has no
`com.unity.polyspatial*`. Part 6's guidance (RealityKit rendering, Shader Graph only,
TextMeshPro only, tier 3 as a visionOS window with tabs) applies to PolySpatial MR and
mostly does *not* apply to a fully-immersive VR build. **This must be decided before
Phase 2.** Adding PolySpatial is a new third-party dependency requiring approval per the
prompt's constraints. Phase 1's visionOS backend will therefore be a compile-only stub
with no PolySpatial reference.

**C5 — Part 2's tier-2 verb table has no row for object *creation*.** Every verb is
scoped to an existing selection, but "Add Cube" has no selection to attach to. Options:
(a) treat creation as a Build-mode in-world tool rather than a menu at all; (b) allow a
"nothing selected" tier 2 context. *Proposed interpretation:* (a) — creation is a Build
mode in-world placement tool, consistent with Part 4 step 2. Flagging for review before
Phase 2 since it is a visible UX change.

**C6 — Part 2 caps tier 1 at four controls and names them: mode indicator, undo, redo,
voice. ERUPT has no undo/redo system at all.** Building tier 1 honestly means building
an undo stack, which is a substantial subsystem the prompt never mentions. Flagging as
Phase 2 scope risk.

**C7 — Part 7 gates on "recorded competence events," but there is no event store.**
`PickPlaceTaskRecorder` records a single task to ROS, not a per-user competence ledger.
Phase 3 needs a persistence decision (PlayerPrefs vs. a study-export file vs. ROS).
