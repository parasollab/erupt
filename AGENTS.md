# Notes for coding agents

ERUPT is a Unity 6 project (the Unity front end for programming robot arms in ROS 2 with
MoveIt 2, on Meta Quest). Read [README.md](README.md) for what it does and the repository
layout. This file holds what is easy to get wrong.

## Where things are

- `Packages/com.erupt.core`: the core. `Packages/com.erupt.plugin.*`: plugins.
  `Packages/com.erupt.robot.*`: robots. `Assets/Erupt.App` and `Assets/Scenes`: the reference
  app. `website/`: the documentation site (DocFX).
- Before changing behaviour, read the relevant part of
  [architecture.md](Packages/com.erupt.core/Documentation~/architecture.md). Before adding a
  feature or any UI, read
  [design-guidelines.md](Packages/com.erupt.core/Documentation~/design-guidelines.md); Part 4
  says where a feature goes and Part 8 is the review checklist. For a plugin, read
  [plugin-authoring.md](Packages/com.erupt.core/Documentation~/plugin-authoring.md).
- The ROS 2 side is a separate repository, [`erupt_ws`](https://github.com/parasollab/erupt_ws).
  Topic names, message layouts and robot descriptions have to agree with it.

## Unity rules

- Every file and folder under `Assets/` and `Packages/com.erupt.*` has a `.meta` file. Commit
  the `.meta` with a new asset, move or delete the two together, and never change a GUID.
- The `*.csproj` and `*.sln` files at the root are generated by Unity and ignored by git. An
  assembly is defined by its `.asmdef`.
- Scripts under `Assets/` go in `Assets/Erupt.App`; nothing may compile into `Assembly-CSharp`.
- Change scenes, prefabs and `.asset` files through the editor or an editor script when you can.
  If you edit the YAML by hand, a reference's `fileID` must point at an object of the type the
  field expects (a `GameObject` is not its `Transform`). The editor reports a mismatch; a
  player build crashes instead. Open the scene in the editor before handing the change over.
- Never run Unity in batch mode while the editor has the project open.
- `Library/`, including `Library/PackageCache`, is not source. The ROS-TCP-Connector and
  URDF-Importer forks come from pinned git URLs in `Packages/manifest.json`: a fix to one goes
  to the fork's repository, then the pin is updated in the manifest and in the `erupt.requires`
  list of the package that asks for it.
- The robot packages hold assets only and are generated; see
  [Tools/robot-descriptions/README.md](Tools/robot-descriptions/README.md). Regenerate them
  instead of editing the prefabs and profiles by hand.

## Architecture rules that CI enforces

The `boundary` job in [.github/workflows/tests.yml](.github/workflows/tests.yml) is a set of
grep checks you can run locally without Unity. The main ones:

- Core never references a plugin, the app or a robot package. Nothing outside
  `com.erupt.plugin.ar` references it, AprilTag or the MR Utility Kit.
- Joint positions are written only in `Packages/com.erupt.core/Runtime/Robot/JointWriter.cs`.
  Everything else moves joints through `IRobotModel`, which keeps the joint limits.
- A plugin takes its ROS bus and its robots from the plugin context (`IEruptContext.Ros`,
  `IEruptContext.Robots`, `RobotInstance.Ros`), not from `RosBus.Instance` or a scene lookup.
- No assumption about the robots: any number, any model. Per-robot ROS names are relative.
- Feature code names no device and has no platform `#if`; that belongs in an input backend.
- All `com.erupt.*` packages carry the same version.

## Tests

- The suites run without ROS on a fake bus (`Erupt.TestSupport`). In the editor:
  **Window > General > Test Runner**. From a shell, with the editor closed and `UNITY` set to
  the editor binary of the version in `ProjectSettings/ProjectVersion.txt`:

  ```bash
  "$UNITY" -batchmode -nographics -projectPath "$PWD" -buildTarget Android \
    -runTests -testPlatform EditMode -testResults "$PWD/Logs/EditMode.xml" -logFile "$PWD/Logs/EditMode.log"
  ```

  Use `PlayMode` for the larger suite; it takes several minutes. Judge a run by the counts in
  the results file, as CI does, not by the exit code: the editor can crash while it shuts down
  after a complete, passing run, and CI only warns about that. For a compile check only, replace
  the test arguments with `-quit` and search the log for `error CS`.
- A PlayMode run can leave an empty `Assets/StreamingAssets` folder and change a line in
  `Assets/XR/Settings/OpenXR Package Settings.asset`. Do not commit either.
- Test plugins with three robots (`FakeRobots.Three`), not one or two.
- A fake bus cannot show that the ROS side agrees. When a change touches what goes over the
  wire, say that the live tests need running: `Tools/live-tests.sh single` against a running
  `erupt_ws` stack ([how](Assets/Erupt.App/Tests/Live/README.md)).
- Nothing here tests the headset. Say so when a change affects input, rendering or the
  Android build, so that someone tries it on a Quest.

## Documentation

- A change in behaviour updates the package's `Documentation~` or `README.md` and the matching
  page under `website/guides`. Check the site with
  `docfx build website/docfx.json --warningsAsErrors`; a broken link fails CI.
- The README and the site use British spelling (licence, colour) and call the person using the
  app "the user".

## Git

- The released code is on the `release` branch, and a push to it publishes the site. Work on a
  branch made from `release` and open a pull request against it.
- Do not commit builds (`*.apk`), `Logs/`, or per-machine settings listed in `.gitignore`.
